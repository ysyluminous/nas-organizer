# NAS Organizer 技术方案

## 1. 目标与边界

### 1.1 目标

在绿联 NAS 上以 Docker 方式运行一个数据治理工具，完成：

1. 对 5 个共享卷（约 45 TiB、十万级文件）建立增量索引
2. 按 **归属域 × 文件类型 × 温度层** 三个维度自动分类
3. 检测重复文件并给出清理建议
4. 生成迁移计划，经人工确认后安全执行
5. 热数据自动备份、冷数据索引同步
6. 全程可审计、可回滚

### 1.2 明确不做

- 不做文件内容的语义理解（不提取 PDF 正文、不做 OCR）
- 不自动执行任何写操作（所有变更必须人工确认）
- 不修改文件本身（只移动、复制、重命名）
- 不替代 NAS 的 RAID / 快照 / 异地备份

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                     Docker Container                        │
│                                                              │
│  接入层    只读挂载 5 个共享目录 (/nas/*)                    │
│     ↓                                                        │
│  引擎层    扫描器 → 分类器 → 查重器 → 计划器 → 执行器        │
│     ↓                                                        │
│  索引层    SQLite (文件表 / 标签表 / 计划表 / 操作日志表)    │
│     ↓                                                        │
│  输出层    FastAPI Web 控制台 + CLI + 定时备份任务            │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 模块职责

## 4. 分类模型

### 4.1 三个维度（正交）

| 维度 | 取值 | 判定依据 |
|---|---|---|
| 归属域 domain | 个人 / 工作 / 生活 / 资源 | 路径规则、关键词、文件名 |
| 文件类型 ftype | 音乐/视频/图书/文档/图片/软件/压缩包/其他 | 扩展名 + magic bytes |
| 温度层 temp | 热 / 温 / 冷 | mtime/atime、大小、所在卷 |

### 4.2 判定优先级（逐级兜底）

```
1. 路径规则    → 命中率约 90%，如 /分享内容/电影/ → 生活·视频
2. 扩展名      → 确定类型，如 .flac → 音乐
3. 文件名关键词 → 确定归属，如 "合同/报表/项目" → 工作
4. 轻量模型    → fastText / TF-IDF，CPU 毫秒级，只处理未命中项
   ├─ 置信度 ≥ 0.8 → 自动归类
   └─ 置信度 < 0.8 → 进人工确认队列
```

### 4.3 温度判定规则

```python
if_atime_90d or mtime_90d or path_in_hot_mount  -> 热
elif atime_365d or mtime_365d                   -> 温
else                                            -> 冷
# 大文件 > 2GB 且超过 1 年未访问，强制冷
```

## 5. 重复检测（三级漏斗）

针对 12 万+ 文件，不能全量哈希，采用三级过滤：

| 级别 | 方法 | 目的 |
|---|---|---|
| 1 | 按文件大小分组 | 排除 95% 以上的文件，只比对同大小的 |
| 2 | 头 64KB + 尾 64KB 哈希 | 快速排除大小相同但内容不同的 |
| 3 | 全量 SHA-256 | 最终确认，只对二级筛后的少数文件做 |

重复组按"保留策略"选出主文件：路径最短 > 层级最浅 > mtime 最新 > 文件名排序。其余标记为"可删除候选"，仍须人工确认。

## 6. 数据库表设计

见 [数据库设计.md](数据库设计.md)。核心表：

- `files` — 文件索引（路径、大小、时间、哈希、domain、ftype、temp、confidence）
- `tags` — 标签定义
- `file_tags` — 文件-标签多对多
- `plans` — 迁移计划单
- `plan_items` — 计划明细（源路径、目标路径、动作、状态）
- `op_logs` — 操作日志（用于回滚）
- `scan_state` — 扫描状态（增量游标）

## 7. 安全执行流程

```
用户确认计划
    ↓
1. 复制：src → dst.tmp（保留源文件）
    ↓
2. 校验：size + SHA-256 一致
    ↓
3. 删除：仅当校验通过，删除 src（mv 到回收站目录，不物理删除）
    ↓
4. 记录：写入 op_logs（含 src/dst/hash/time）
    ↓
回滚：根据 op_logs 反向恢复
```

**绝不直接 mv**：跨盘 mv 在 btrfs 上是 copy+delete，中途失败会丢数据。

## 8. 备份策略

| 数据类型 | 策略 |
|---|---|
| 个人 + 工作（不可再生） | rsync 到 volume5 + 外置盘/云端离线副本 |
| 音乐/影视/电子书（可再生） | 单份即可，不备份 |
| 配置文件 + 索引库 | 每日打包备份到 volume5 |

## 9. 分阶段开发计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | 只读扫描 + 索引 | 能扫完 5 个卷，索引入库，性能可接受 |
| P1 | 规则分类 + 重复报告 | 分类准确率抽样 > 95%，重复组正确 |
| P2 | Web 控制台 + 手动执行 | 能预览计划、逐条确认、执行可回滚 |
| P3 | 热备份 + 冷同步 | rsync 定时备份，校验通过 |
| P4 | 模型兜底 | 训练 fastText，低置信度件自动归类 |

## 10. 性能考虑

- 12 万文件 stat 采集：预计 2-5 分钟，增量扫描只处理变更文件
- 三级哈希：一级过滤后通常只剩 5%-10% 进入二级，最终全量哈希 < 1%
- SQLite 索引：为 `path`、`size`、`mtime`、`ftype`、`domain`、`temp` 建索引
- Web 分页查询，避免一次加载全部记录

## 11. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 无 RAID，单盘故障全丢 | 关键数据双份、离线备份、启用 btrfs 快照 |
| 自动移动误判 | 默认 dry-run、人工确认、每步可回滚 |
| 扫描期间文件变化 | 记录扫描时间点，变更后增量重扫 |
| 哈希计算占用 CPU | 限制并发数、低峰时段运行、可配置 |
